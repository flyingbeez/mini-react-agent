## A 类 · Agent 架构

### A1. 介绍一下你这个项目

**答（60 秒版）**：
> 我用零依赖的方式从零写了一个 ReAct Agent 内核，大概 300 行核心代码，配了 103 个单元测试。
> 动机是我发现用 LangChain 能跑起来，但说不清内部循环是怎么工作的，尤其是出错的时候不知道怎么定位。
> 所以我把循环、工具抽象、消息协议、轨迹记录、死循环防护都自己实现了一遍。
> 里面比较有意思的是我用一个 MockLLM 把"模型行为"变成了可编程的依赖，所以整个测试套件不需要 API Key、
> 一秒内跑完，而且能稳定复现"模型调错工具后自我纠正"这类场景。

**为什么这样说有效**：有动机、有具体做法、有可验证的数字（103 测试、零依赖、一秒）。

### A2. 为什么不用 LangChain？

> 不是不用，是分工不同。做业务我仍然会用框架，生态和可观测性更成熟。
> 但这个项目的目的就是搞清楚框架内部在干什么。
> 实际收益是：上周线上 Agent 出现"反复调同一个接口"，我能直接判断是我们的工具返回值格式变了导致模型
> 一直重试，而不是靠猜。这个判断力来自我自己写过循环和错误处理。

**注意**：不要贬低框架。说"框架不好"是减分项，说"我知道框架内部做了什么"是加分项。

### A3. Agent 循环什么时候停？

> 三个终止条件：模型这一轮没返回 `tool_calls`（正常结束）、达到 `max_steps`（兜底）、
> 检测到重复调用（异常结束）。不能只靠第一个，因为模型确实会卡在循环里出不来。

### A4. 只设 `max_steps` 为什么不够？

> `max_steps` 只是"慢慢死"，它不会让模型知道它卡住了。而且到上限时你只拿到一句"任务未完成"，
> 没有任何可用信息。所以我加了重复检测：对 `(工具名, 排序后的参数)` 做签名计数，
> 第二次重复时注入一句提示让模型换策略，超过阈值才终止，并且终止时把已获得的有效信息摘要返回。
> 这样既止损，又保留了部分价值。

### A5. 工具报错了你会怎么办？

> 分三层。第一层，工具层把所有异常统一包装成 `ToolError`；
> 第二层，Agent 层把它转成一条 `[工具错误] ...` 的 observation 回灌给模型，循环不中断；
> 第三层，错误文案必须告诉模型"下一步怎么办"，比如"岗位 id 不存在，请先调用 list_jobs"，
> 而不是只写"invalid argument"。因为在 Agent 系统里错误信息是 prompt 的一部分，不是给程序员看的日志。

## B 类 · Function Calling / 协议细节

### B1. 一次 function calling 的请求和响应长什么样？

> 请求里 `tools` 是一个**请求参数**，不是消息，格式是
> `{"type":"function","function":{"name":..., "description":..., "parameters": <JSON Schema>}}`。
> 模型不执行函数，它返回 `choices[0].message.tool_calls`，里面每项有 `id`、`function.name`、
> `function.arguments`（是一个 **JSON 字符串**，不是对象）。
> 然后我把 assistant 消息原样塞回 messages，再补一条 `{"role":"tool","tool_call_id":<id>,"content":<结果字符串>}`，
> 发起第二次请求。

### B2. 这一步最常见的报错是什么？

> 两个。第一，忘了把 assistant 的 `tool_calls` 原样带回 messages，或者每个 `tool_call_id` 没有对应的
> `tool` 消息，服务端会直接 400。第二，以为 `arguments` 已经是字典，直接当 dict 用，
> 实际它是字符串，得 `json.loads`。而且这个字符串**不保证是合法 JSON**，必须做容错。

### B3. 一轮里模型调了多个工具，怎么处理？

> `tool_calls` 是数组，可以并行执行，然后为每个 `id` 各回一条 `tool` 消息。
> 顺序执行也没问题，但要注意 `tool_call_id` 必须一一对应。
> 我这个仓库目前是顺序执行，并行化是我列在 TODO 里的 —— 面试时可以主动说这是已知限制。

### B4. 文本 ReAct 和原生 function calling 你怎么选？

> 生产优先原生：格式约束在模型采样阶段就生效了，比正则可靠。
> 文本模式用于不支持 tools 的模型、或者需要模型输出更多中间推理的场景。
> 另外自己写一遍文本解析器能真正理解"框架替你做了什么"——
> 我那个 `parser.py` 要处理加粗、全角冒号、单引号 JSON、跨行 JSON、甚至模型自己脑补假 Observation。

## C 类 · 工程与可观测性

### C1. 你怎么知道 Agent 的效果好不好？

> 靠结构化轨迹，不是靠肉眼看日志。每一轮都记 thought、action、参数、observation、成功与否、耗时、token。
> 有了这些就能算四个指标：任务成功率、工具调用失败率、平均步数、单任务平均 token 成本。
> 失败率突然升高通常说明工具描述或参数 Schema 有问题；步数变多通常说明规划能力退化或者提示词被改坏了。

### C2. 成本失控怎么办？

> 三个手段：给 observation 做截断（工具返回一大坨 JSON 是最常见的元凶）、
> 限制 `max_steps`、以及把稳定的系统前缀交给 prompt caching。
> 我这个项目里每一步都记了 token，所以成本是可见的 —— 不可见就没法优化。

### C3. 你怎么测一个 Agent？

> 核心思路是把模型变成可编程的依赖。我用 `MockLLM`，测试里给它一个脚本，它按顺序返回预设响应。
> 这样能精确构造"先调错工具、再改对"、"永远不给答案"、"返回非法 JSON 参数"这些边界场景，
> 而且不花钱、不抖动、一秒跑完。真实模型的测试会放到单独的评测集里，做端到端成功率统计，不进单测。

### C4. 你写的测试里最有价值的是哪一条？

> `test_different_args_are_not_treated_as_loop`。它是反向案例：验证参数不同的重复调用**不会**被误判成死循环。
> 因为死循环检测这种东西，写正向案例很容易过，但阈值调紧一点就可能把正常的九步任务误杀。
> 反向案例才是防回归的。

## D 类 · 深挖与压力测试

### D1. 你这个项目有多少是你自己写的？

**诚实回答法**（重要）：
> 核心代码是我自己设计并实现的，代码结构和测试也是我搭的。
> 但我用了 AI 辅助来加快文档和部分样板代码的编写，
> 所以我能逐行解释每一处设计取舍 —— 比如为什么死循环检测要用参数签名而不是只看工具名，
> 为什么参数校验要允许忽略多余字段。

**千万不要说"全都是我手写的"**。面试官只要追问一个细节就能判断出来，
而且这类项目的特点是代码不多，深挖成本很低。**AI 辅助不是减分项，"讲不清楚"才是。**

### D2. 如果让你把它改成支持多轮对话，你会怎么改？

> 把 `history` 从"调用方传入的列表"改成 Agent 自己维护的会话对象，
> 并且加一个上下文管理策略：token 超过阈值时，把早期轮次做摘要压缩，保留最近 N 轮原文。
> 关键是要把"摘要"这一步也记进 trace，否则出问题没法追。
> 我没有一上来就做，是因为这属于产品层需求，会掩盖核心循环的可读性。

### D3. 现在让你上线，你还缺什么？

主动列清楚（这一题答得好，比前面所有题都能加分）：

> 1. **流式输出**：现在长回答用户会一直干等，体验不行。
> 2. **超时与并发控制**：单次工具调用没有独立超时，一个慢工具会拖死整轮。
> 3. **可观测性接入**：自己的 trace 只能本地看，上线要接 OpenTelemetry 或者 Langfuse。
> 4. **权限与安全**：工具现在没有权限分级，能读文件、能算数，但没有沙箱边界。
> 5. **评测集**：现在只有单元测试，缺端到端任务成功率的回归评测。
> 6. **成本上限**：只有步数上限，没有 token 预算上限。

### D4. 你觉得这个项目的技术难点在哪？

> 不是循环本身，循环二十分钟就能写出来。难点在**"模型不按规矩来"的所有分支**：
> 参数不是合法 JSON、工具名编造、自己脑补 Observation、反复调同一个工具、
> 一轮调十个工具把上下文撑爆。这些论文里不写，但决定了它是 demo 还是能用的东西。
> 我花时间最多的地方在 `parser.py` 和错误处理，而不是 `agent.py`。

## E 类 · 反问面试官（必问，但要问得有水平）

不要问"公司福利怎么样"。挑这些问题：

1. 团队现在的 Agent 是偏 workflow 编排还是自主决策？线上对"模型自主决定下一步"的容忍度到什么程度？
2. 你们的 Agent 效果是怎么量化的？有没有固定的评测集和回归机制？
3. 工具（Tool）这一层是由业务团队自己维护，还是有统一的平台？
4. 目前最头疼的是效果问题、成本问题还是稳定性问题？

**为什么这样问**：它们显示你关心的是工程落地，而不是"能不能用上最新框架"。
