# 01 · ReAct 原理与 Agent 循环

> 目标：读完这一篇，你能在白板上画出 Agent 循环，并解释每一步为什么存在。

## 1. 先分清三个词：LLM、Agent、Workflow

| 概念 | 一句话定义 | 例子 |
|---|---|---|
| **LLM** | 输入文本，输出文本的模型 | 你问"北京天气"，它凭记忆瞎编一个温度 |
| **Workflow** | 人把步骤写死，模型只填内容 | 固定的"抽取 → 翻译 → 摘要"三段流水线 |
| **Agent** | **模型自己决定下一步做什么**，包括调哪个工具、调几次、什么时候停 | 模型先查天气 API，发现要对比两座城市，于是又查了一次 |

**关键区别**：Workflow 的控制流是人写的；Agent 的控制流是模型生成的。
所以 Agent 的能力上限取决于两件事 —— 模型的决策质量，以及你给它的工具质量。

面试里常见的追问："什么时候不该用 Agent？"
答案：**当步骤固定、可枚举时，Workflow 更快、更便宜、更可控**。
Agent 的价值在于处理"路径不确定"的任务。给一个确定性任务套 Agent 是过度设计。

## 2. ReAct 是什么

ReAct = **Rea**soning + **Act**ing，2022 年由 Yao 等人提出（[arXiv:2210.03629](https://arxiv.org/abs/2210.03629)）。

它要解决两个极端的问题：

- **纯推理**（Chain-of-Thought）：模型没有外部信息来源，遇到需要实时数据或精确计算时就编（幻觉）。
- **纯行动**：模型机械地调工具，但不做规划，调错了也不知道怎么补。

ReAct 的做法是**交替进行**：

```
Thought      →  我需要知道当前的汇率
Action       →  get_exchange_rate(currency="USD", target="CNY")
Observation  →  7.12
Thought      →  100 美元 = 712 元，可以回答了
Final Answer →  约 712 元人民币
```

其中：
- **Thought** 是模型的内部推理，不产生副作用，但强制它"说出计划"能显著提升决策质量。
- **Action** 是唯一有副作用的环节，必须由**你的代码**去执行（模型永远不直接执行函数）。
- **Observation** 是工具返回的客观事实，它把模型从"猜"拉回"看"。

### 为什么 Thought 有用

这不是玄学，而是**把隐式计算变成显式 token**。模型在生成 `Action` 之前先生成一段推理，
相当于给它自己做了 chain-of-thought，后面的决策就建立在这段文字上。
工程上的副作用是：Thought 会占用输出 token，也会泄露模型的中间假设，所以线上有时会要求它简短。

## 3. 一次完整的循环（逐帧拆解）

以本仓库的 `native` 模式为例：

```
第 0 步  组装 messages
        [
          {"role": "system",    "content": "你是 Agent，可用工具：..."},
          {"role": "user",      "content": "帮我算 (365*24-100)/7"},
          {"role": "tools",     ...}                 ← 工具声明，不是消息，是请求参数
        ]

第 1 次调模型 → 返回
        {
          "content": "我需要精确计算。",
          "tool_calls": [{"id": "call_1",
                          "function": {"name": "calculator",
                                       "arguments": "{\"expression\": \"(365*24-100)/7\"}"}}]
        }

第 1 步  你的代码执行 calculator(...)  →  "1237.142857"
        把两条消息追加进 messages：
        {"role": "assistant", "content": "我需要精确计算。", "tool_calls": [...]}
        {"role": "tool", "tool_call_id": "call_1", "content": "1237.142857"}

第 2 次调模型 → 返回 content，且 tool_calls 为空
        → 循环结束，把 content 作为最终答案
```

**三个必须记住的细节**：

1. `tools` 是**请求参数**，不是消息。它在告诉模型"你能用哪些工具"，而不是"你用了工具"。
2. `assistant` 消息里必须**原样带上 tool_calls**，并且每个 `tool_call_id` 都要有一条对应的 `tool` 消息，
   否则 OpenAI / DeepSeek 会直接报 400。这是新手最常见的报错。
3. 循环的终止条件是**"模型这一轮没有返回 tool_calls"**，而不是"模型说了某个关键词"。

## 4. 两种模式：原生 Function Calling vs 文本 ReAct

**原生 Function Calling**：模型厂商在训练时就教会了模型输出结构化的 `tool_calls` 字段。

**文本 ReAct**：完全靠提示词约定格式，模型输出自由文本，你用正则解析。

```
文本模式的实际输出（可能长这样）：

**Thought**: 我需要检索
**Action**: `search_notes`
**Action Input**: {'query': 'ReAct', 'top_k': 1}      ← 注意：单引号，非法 JSON
```

文本模式的解析要处理 markdown 加粗、中英文冒号、单引号、多行 JSON、`key=value`……
本仓库的 `parser.py` 把这些都兜住了。这也是为什么**生产环境优先用原生 function calling**：
厂商把格式约束做进了采样过程，比你的正则可靠得多。

那文本模式还有什么用？
- 用不支持 tools 的老模型 / 本地小模型时。
- 需要模型"边想边说"更多中间过程时。
- **教学**：自己写一遍解析器，才真正理解框架替你做了什么。

## 5. 循环必须有的四道保险

只看论文会写出一个"理论上能跑"的 Agent；上线后会遇到下面四种情况：

| 症状 | 后果 | 对策 |
|---|---|---|
| 模型永远在调工具，不给答案 | token 烧光、请求超时 | `max_steps` 硬上限 |
| 模型反复用**相同参数**调同一个工具 | 死循环，永远出不来 | 对 `(工具名, 参数)` 做签名计数，先注入纠正提示，再强制终止 |
| 工具抛异常 | 整个 Agent 崩掉 | 把异常转成 `[工具错误] ...` 文本回灌给模型 |
| 工具返回超长内容 | 上下文爆炸、成本失控 | 截断 observation 并标注 |

其中第二条最容易被忽略。仅仅设置 `max_steps` 是不够的 —— 那只是"慢慢死"，你还得让模型**知道它卡住了**。
本仓库的做法是：重复到第 2 次时注入一句"你刚才重复调用了工具 X，请换一种做法"；
到第 4 次还没改，就带着已获得的信息终止，并说明卡在哪里。

## 6. 为什么错误信息要"教模型怎么办"

对比两种错误写法：

```python
# 写法 A
raise ValueError("invalid job_id")

# 写法 B（本仓库示例的做法）
raise ToolError("岗位 id 'agent' 不存在。请先调用 list_jobs 获取合法 id。")
```

写法 A 回灌给模型后，模型只知道"错了"，很可能原样再试一次。
写法 B 直接给出了**下一步动作**，模型大概率能自我纠正。

这背后的原则是：**在 Agent 系统里，错误信息不是给程序员看的，是给模型看的**。
它是一个 prompt，所以要写清楚"错在哪 + 怎么办"。

## 7. 从 ReAct 到更复杂的架构

ReAct 是起点，不是终点。理解它之后再往上走：

| 架构 | 解决的问题 | 代价 |
|---|---|---|
| **ReAct** | 边想边做，适合 3-8 步的短任务 | 长任务容易迷路、容易重复 |
| **Plan-and-Execute** | 先规划出子任务列表再执行，适合长链条 | 规划错了整条链都错，需要 Replan |
| **Reflection / Reflexion** | 执行后自我批判并重试 | 成本和延迟翻倍 |
| **Multi-Agent** | 角色分工（规划者/执行者/评审者） | 通信开销大，容易互相甩锅 |
| **RAG + Agent** | 把知识检索变成工具之一 | 检索质量决定上限 |

**面试建议**：不要一上来就说"我用多 Agent"。先讲清楚"为什么单 Agent + 工具不够用"，
再说多 Agent 带来的额外成本。技术选型的理由比技术名词值钱。
