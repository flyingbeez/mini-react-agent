# 02 · 代码导读

> 按数据流顺序读，五个模块，每个模块只做一件事。

## 数据流总览

```
用户问题
   │
   ▼
agent.py ──► llm.py ──► HTTP /chat/completions ──► 模型
   │            ▲
   │            └── LLMResponse(content, tool_calls, tokens)
   ▼
parser.py（文本模式）或 直接读 tool_calls（原生模式）
   │
   ▼
tools.py ──► 你的业务函数
   │
   ▼
trace.py ◄── 每一步都记一条
```

## 1. `llm.py` —— 把模型变成一个可替换的依赖

**要解决的核心问题**：测试不能依赖真实 LLM（慢、贵、不稳定、不可复现）。

三种实现的关系：

```
BaseLLM (chat 接口)
   ├── MockLLM           ← 脚本 / 函数驱动的假模型，测试和 demo 用
   └── OpenAICompatLLM   ← 真模型，只用标准库 urllib
```

关键设计是 `MockLLM`：它让"模型行为"变成**可编程的输入**。
于是测试可以这样写：

```python
llm = MockLLM([
    LLMResponse(tool_calls=[ToolCall(name="add", arguments='{"a":2,"b":3}')]),
    LLMResponse(content="结果是 5"),
])
result = ReActAgent(llm, registry, mode="native").run("2+3")
assert result.answer == "结果是 5"
```

`MockLLM` 还会记录 `self.calls`，测试可以断言"第二次请求里带了两条 tool 消息"——
**这才能验证你确实按协议格式回传了工具结果**，而不是只测了最终字符串。

`OpenAICompatLLM` 用 `urllib` 手写 HTTP，为的是让你看清请求体长什么样：

```json
{
  "model": "deepseek-chat",
  "messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}],
  "tools": [{"type": "function", "function": {"name": "...", "parameters": {...}}}],
  "tool_choice": "auto",
  "temperature": 0
}
```

注意几个工程细节：
- **重试 + 指数退避**：网络抖动重试有意义，`401/404` 重试无意义，直接抛。
- `usage.prompt_tokens / completion_tokens` 被提取出来，一路传到 trace，用于成本统计。
- 没有 `choices` 的异常响应会被显式报错，而不是 `KeyError` 糊过去。

## 2. `tools.py` —— 工具层，写代码最容易偷懒的地方

### 2.1 Schema 自动生成

```python
@tool
def get_weather(city: str, days: int = 1) -> dict:
    """查询指定城市未来几天的天气。

    Args:
        city: 城市名，例如 "Beijing"
        days: 预报天数，1-7
    """
```

从类型注解 + docstring 推出：

```json
{"type": "object",
 "properties": {"city": {"type": "string", "description": "城市名，例如 \"Beijing\""},
                "days": {"type": "integer", "description": "预报天数，1-7", "default": 1}},
 "required": ["city"]}
```

**为什么值得自己做**：手写 Schema 一定会和函数签名漂移。
改了参数忘了改 Schema，模型就会传错参数，而你会在半夜查日志。
自动生成让"文档即实现"。

支持的注解：`str/int/float/bool/list[X]/dict`、`Optional[X]`、`X | None`、`Literal[...]`、`Annotated[X, "说明"]`。

### 2.2 参数校验：宽容但有底线

模型经常把 `5` 写成 `"5"`，把 `true` 写成 `"true"`。`_coerce()` 做**保守纠偏**：
只在无歧义时转换（`"5" → 5`），`"abc"` 直接报错。

两条底线：
- `True` 不能当成整数 `1`（Python 里 `isinstance(True, int)` 为真，不拦就会出错）。
- 多余参数**忽略**而不是报错 —— 模型多塞字段比少塞字段常见，报错会让它陷入无意义的重试。

### 2.3 错误即观察

```python
def run(self, args):
    cleaned = self._check(args)          # 参数错误 → ToolError
    try:
        result = self.func(**cleaned)
    except Exception as exc:
        raise ToolError(f"{self.name} 执行出错：{type(exc).__name__}: {exc}")
    return result if isinstance(result, str) else json.dumps(result, ensure_ascii=False, ...)
```

任何异常都被统一包装成 `ToolError`，由 `agent.py` 转成 observation 回灌。
**Agent 的可恢复性就来自这一层**。

## 3. `parser.py` —— 文本模式的脏活累活

文本 ReAct 的现实是：模型会用 `**Action**:`、全角冒号、`` ` `` 包代码、
单引号 JSON、跨行 JSON、甚至直接吐一个 JSON 对象。

`parse_arguments()` 的降级链：

```
标准 json.loads
   ↓ 失败
单引号 → 双引号 / 裸键名加引号  → 再试 json.loads
   ↓ 失败
key=value 形式解析（a=1, b=hello，值做 int/float/bool 推断）
   ↓ 失败
返回 None（交给上层决定：单参数工具就直接填，多参数工具就报格式错误）
```

`parse_react_text()` 的判断顺序很重要：

1. 先看是不是一个 JSON 对象（模型偷懒时直接吐 `{"action": ..., "action_input": ...}`）。
2. 再看 `Final Answer` —— 并且要求它出现在 `Action` **之前**，否则说明模型先做了动作又说答案。
3. 再抽 `Action` / `Action Input`，并把 `Action Input` 在遇到 `Observation`/`Thought` 标记时截断。

最后一条很容易被忽略：模型经常自己脑补一个假的 `Observation` 写进去。
截断能防止把模型的幻觉当成工具结果。

## 4. `trace.py` —— Agent 的可观测性

`Step` 记录：`thought / action / action_input / observation / ok / error / latency_ms / prompt_tokens / completion_tokens / mode`。

`AgentTrace` 聚合：工具调用数、失败数、token 总量、结束原因。

**为什么这比日志重要**：有了结构化轨迹，才能计算指标：

| 指标 | 算法 | 说明 |
|---|---|---|
| 任务成功率 | `stopped_reason == "final_answer"` 且答案通过校验 | 最核心 |
| 工具调用准确率 | 失败调用 / 总调用 | 反映 Schema 和描述的质量 |
| 平均步数 | `len(steps)` | 反映规划效率 |
| 单任务成本 | `total_tokens` × 单价 | 反映能不能上线 |

`render()` 输出人类可读轨迹，`to_json()` 输出结构化轨迹，两者都有人用：
调试看前者，评测和看板用后者。

## 5. `agent.py` —— 循环本体

读这个文件时，抓住 `_loop_native` 和 `_loop_text` 两个方法即可，它们结构完全对应。

`_loop_native` 的关键行：

```python
response = self.llm.chat(messages, tools=self.tools.specs())   # ① 带上工具声明
if not response.tool_calls:                                    # ② 终止条件
    return response.content
messages.append(response.assistant_message())                  # ③ 原样回传 tool_calls
for tc in response.tool_calls:                                 # ④ 一轮可能多个工具
    observation = self._execute(step, tc.name, tc.args())
    messages.append({"role": "tool", "tool_call_id": tc.id, "content": observation})
    verdict = self._check_repeat(state, signature, tc.name)    # ⑤ 死循环检测
```

`_check_repeat` 返回三种结果：

```
repeat_counts[signature] += 1
  count >= repeat_stop_at  → "stop"   带上已获得信息终止，stopped_reason = "loop_detected"
  count >= loop_threshold  → "nudge"  注入提示词："你重复调用了 X，请换一种做法"
  否则                      → ""
```

`signature` 用 `json.dumps(args, sort_keys=True)` 生成，保证 `{"a":1,"b":2}` 和 `{"b":2,"a":1}` 是同一个签名。

## 6. 测试思路（这部分比代码更值得学）

`tests/test_agent.py` 覆盖的是**行为**，不是**实现**：

| 测试 | 验证的行为 |
|---|---|
| `test_parallel_tool_calls_in_one_turn` | 一轮多个工具时，两条 `tool` 消息都按 id 正确回传 |
| `test_unknown_tool_becomes_observation_then_recovers` | 工具名错误 → 不崩 → 模型能改对 |
| `test_invalid_json_arguments_reported_to_model` | 参数非法 → 错误信息准确（而不是报成"工具不存在"） |
| `test_max_steps_guard` | 模型永不停 → 停在 `max_steps` |
| `test_loop_detection_stops_repeats` | 重复调用 → `loop_detected` |
| `test_different_args_are_not_treated_as_loop` | 参数不同 → **不能**误判为死循环（反向案例） |
| `test_loop_nudge_is_injected` | 提示词确实被注入了 messages |
| `test_long_observation_truncated` | 超长结果被截断 |

**写测试时最容易犯的错是只写正向案例。**
`test_different_args_are_not_treated_as_loop` 这种反向案例才是防回归的关键 ——
它保证你调优死循环阈值时不会把正常的多步任务误杀。

## 7. 建议的动手练习（从易到难）

1. **加一个工具**：`get_weather(city: str, days: int = 1)`，跑 `examples/03_custom_tool.py` 改一改。
2. **加一个断言测试**：验证"同一轮里两个工具的 token 被分别记录"。
3. **加流式输出**：给 `OpenAICompatLLM` 加 `stream=True` 的支持，边生成边打印。
4. **把 observation 截断改成"摘要"**：调用模型把长结果压缩成一句话再回灌。
5. **加并行工具执行**：把 `for tc in response.tool_calls` 改成线程池或 `asyncio.gather`。
6. **加一个评测脚本**：跑 10 条固定问题，统计成功率、平均步数、平均 token。

做完 3 和 5，你对"Agent 工程"的理解会超过大多数只会调框架的人。
