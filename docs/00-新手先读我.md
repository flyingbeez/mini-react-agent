# 00 · 新手先读我

> 这篇假设你**完全没写过这类程序**。不出现没解释的词。
> 全部看完大概 10 分钟。
>
> 看完的标准：你能用自己的话跟别人讲清楚"Agent 是怎么工作的"。
>
> 如果有一段看不懂——**是我的问题，不是你的问题**。直接告诉我哪一段，我重写。

## 一、先讲个故事

你要出差，让助理订机票。

**情况一：你用了一个"只会说话的顾问"**

你问："帮我订张明天去上海的机票。"
顾问回答："好的，建议您预订明天上午的航班，价格大约 800 元。"
—— 他说得很好，但**他什么都没做**。机票还在那儿没订。

**情况二：你用了一个"能办事的助理"**

你说同样的话。助理的做法是：

1. **想**：得先看看明天有哪些航班
2. **做**：打开订票系统，查了一下
3. **看**：查到 3 个航班，最早 8 点，800 元
4. **再想**：8 点太早，看看有没有 10 点左右的
5. **做**：又查了一次
6. **看**：10:20 有一班，850 元
7. **再想**：这个可以，订它
8. **做**：下单
9. **看**：出票成功
10. **回答**："已为您订好明天 10:20 的航班，850 元。"

**注意：情况二里，助理"想 → 做 → 看"来来回回了好几遍。**

**这就是 Agent。** 它和"只会说话的顾问"最大的区别是：**它会动手，会根据结果调整，会一直做到完成为止。**

---

## 二、把这个故事翻译成技术名词

上面那个故事，在技术界有个名字叫 **ReAct**。
它是两个英文单词拼起来的：

- **Re** = Reasoning = **推理** = 就是"想"
- **Act** = Acting = **行动** = 就是"做"

所以 **ReAct = 边想边做**。

对应关系是这样的：

| 故事里的动作 | 技术名词 | 英文 |
|---|---|---|
| 想 | 思考 | Thought |
| 做 | 动作 / 调用工具 | Action |
| 看 | 观察结果 | Observation |
| 回答 | 最终答案 | Final Answer |

**记住这四个词，你就已经掌握了这个项目 80% 的内容。**

因为整个程序的主循环，就是这四步在转圈：

```
     ┌─────────────────────────────────────────┐
     │                                         │
     ▼                                         │
  想一想 ──► 做一个动作 ──► 看看结果 ──────────┘
   │                          （结果喂回去给它看）
   │
   └──► 如果已经能回答了 ──► 给出最终答案，结束
```

## 三、为什么不能一步到位？

你可能会想：**为什么要这么麻烦？直接让 AI 回答不就行了？**

三个原因，都很实在：

### 原因 1：它有些事根本不知道

AI 的知识是"训练时"灌进去的，停在某个时间点。
你问它"现在几点了""今天股价多少""我们公司的报销标准"——它不知道。

但它**不承认自己不知道**，它会编一个看起来很像的答案。这个毛病叫**幻觉**。

给它一个"查时间"的按钮，它就能查到真实答案。

### 原因 2：它算数不太行

这是很多人不知道的事：**大模型做数学题经常算错**。

不是它笨，是它的工作原理决定的——它是"猜下一个字最可能是什么"，
不是"按数学规则算"。比如你问它 13 × 27，它可能答 361（正确是 351）。

给它一个"计算器"按钮就没这问题了。

### 原因 3：有些答案要好几步才能拼出来

比如："帮我查一下上海和杭州明天的天气，哪个更适合出去玩？"

这需要：查上海 → 查杭州 → 对比 → 给建议。**四步，不是一步。**

一次让 AI 全做完，它很容易在中间漏掉一环。
拆成四步、每步都能看到结果，就可靠得多。

## 四、现在看一个真实例子（重点）

问 AI 这句话：

> "帮我算 (365 × 24 - 100) ÷ 7"

**第 1 轮：**

AI 收到问题，先"想"了一下，然后吐出一段东西：

```
Thought: 这需要精确计算，我用手边的计算器。
Action: calculator
Action Input: {"expression": "(365*24-100)/7"}
```

翻译成人话：

- `Thought`（想）：我要用计算器
- `Action`（做）：我要按"计算器"这个按钮
- `Action Input`（参数）：按的时候输入这串算式

**这很重要的一点**：AI 只是**说它想按按钮**，它自己没法真的按。
**是"你的程序"看到了它这句话，去真的执行了计算器。**

这是很多人搞混的地方：**AI 负责决定，程序负责执行。**

**第 2 轮：**

程序的执行结果 `1237.142857` 被喂回给 AI。AI 这次说：

```
Thought: 算出来了，可以回答。
Final Answer: 约等于 1237.14
```

程序看到 `Final Answer`，就知道该结束了，把答案给用户。

**全程结束。一共 2 轮。**

## 五、那些"坑"（这才是这个项目的真正价值）

如果只写到上面那样，程序跑起来是没问题的——**前提是 AI 一直很听话**。

但真实情况是 AI 经常不听话。下面四种情况一定会在真实使用中出现：

### 坑 1：它停不下来

它会一直按按钮，永远不说 `Final Answer`。
每按一次就要花钱（调 AI 是收费的），一直按下去成本就爆炸了。

**解决**：设个上限。"最多试 8 次，第 9 次还不给答案，就强制停下。"

### 坑 2：它卡住了（最隐蔽的一个）

它会**用一模一样的参数，反复按同一个按钮**。
每次得到的结果都一样，但它还是继续按。

你会看到它在那转圈，转到次数上限耗尽为止。

**解决**：记住它按过什么。如果发现"同样的按钮 + 同样的参数"出现第 2 次，
就提醒它一句："你刚才已经这样试过了，换个办法。"

如果提醒了还是不改，就直接停下，并把它已经查到的信息交出来
（这样至少不是白跑一趟）。

> **这一条我特别想让你记住：**
>
> 很多人以为"设个次数上限"就解决了。不是的。
> **上限只是让它"慢慢死"。真正有用的是让它"知道自己卡住了"** ——
> 这样它才有机会换个办法。
>
> 这个思路在很多地方都通用：**发现异常时，第一反应应该是"给出有用的反馈"，而不只是"掐断"。**

### 坑 3：按钮坏了

按"查天气"按钮，结果网断了，报了个错。

如果程序直接崩了，用户就只看到一片红字，什么也没有。

**解决**：不要崩。把"这个按钮坏了"这件事本身，当成一条消息告诉 AI。
AI 看到之后会想办法："查天气不行，那我告诉你现在查不了。"

**这个设计有个说法叫"错误即信息"**——
在 Agent 系统里，报错不是给程序员看的，是**给 AI 看的**。
所以报错要写得让 AI 看得懂、知道下一步怎么办。

### 坑 4：按钮吐出一大堆东西

按"查资料"按钮，返回了 10 万字的文章。

全喂给 AI 的话，一是可能超出它的处理上限，二是**特别费钱**（按字数收费）。

**解决**：太长就截断，只留前面一部分，并标明"这里被截断了"。

## 六、你可以怎么验证自己懂了

跑一下这个命令（在项目文件夹里打开命令行）：

```bash
python examples/01_offline_demo.py
```

屏幕上会打出四个演示，每个都显示了 AI 想什么、做什么、结果是什么。

**对着上面的第五节看**：演示会依次展示"正常情况""卡住了""按钮坏了"这几种场景。

然后试着回答这四个问题（不许翻上面）：

1. Agent 和普通 AI 差别在哪？举一个生活里的例子。
2. 想 → 做 → 看，这三步里，**哪一步是 AI 干的，哪一步是程序干的**？
3. 为什么光设"最多试 8 次"不够？还要加什么？
4. 工具报错的时候，为什么不应该让程序崩溃？

答不上来就回去看对应的小节。**能答上来，你就比大多数人都懂 Agent 了。**

## 七、接下来怎么学

按这个顺序，一次只看一样：

1. 跑一遍 `python examples/01_offline_demo.py`，对着输出看本文第四节
2. 打开 `mini_agent/agent.py`，找到那个"想 → 做 → 看"的循环（大概在文件中间）
3. 打开 `mini_agent/tools.py`，看一个"按钮"是怎么做出来的
4. 跑一遍 `python run_tests.py`，看看"自动检查"是怎么写的

**别一次全看。** 看多了会乱，而且记不住。
